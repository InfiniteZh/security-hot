01 系统总览与分层

单进程托管：一个 uvicorn 同时跑 FastAPI 后端与 web/index.html 静态前端。数据底座是双轨的——行业资讯走 SQLite（news.db，WAL + FTS5），漏洞/旁路信号走 JSON 缓存（backend/cache/*.json）。

① 抓取层 Fetch

scripts/fetch_data.py — 12 个 fetcher 异步并发。news→SQLite，其余→JSON。murphy 在此层。

② 富化层 Enrich

embed_articles / cluster_articles / llm_rank。通过 SQLite WAL 与抓取层完全解耦，0 import 关系。

③ 服务层 Serve

backend/app/：main.py(路由) + data.py(归一化 + 30s TTL 内存缓存) + models.py(Pydantic)。

④ 展示层 Web

web/index.html 单文件，i18n，Promise.allSettled 各 panel 独立渲染。

⑤ 投送层 Dispatch

poisoning_dispatch.py → Kafka 供应链投毒情报。独立旁路，下游消费。

⑥ 调度层 Schedule

双模式：bare-metal cron 或进程内 APScheduler。二选一驱动 ①②⑤。

03 整体定时调度逻辑

两种互斥的部署调度模式，驱动同一批脚本、同一套节奏。所有作业最终都经 main.py 的共享锁串行化。

模式 A · Bare-metal cron （docs/cron-template.txt）

宿主有 uv + 仓库时使用。env 经 set -a && . ./.env && set +a 注入。CRON_TZ=UTC。

cron动作说明
*/15 * * * *fetch news --incremental智能挑源（按 interval_minutes，top=30m/tail=4h，故廉价）
0 */2 * * *embed_articles抓取沉淀后再嵌入
15 */2 * * *cluster_articles嵌入后 15min（读预计算向量）
30 */2 * * *llm_rank classify错峰避免 SQLite 写竞争
45 */2 * * *llm_rank summarize
0 23 * * *llm_rank daily_briefUTC 23:00 ≈ 北京次日 7am
30 */4 * * *fetch other（含 murphy）kev,ghsa,pocs,murphy,itw,heat,epss,osv,nuclei,hn,masto

→ 墨菲在"other"桶里，每 4 小时刷新一次，不在 15 分钟新闻环内。

模式 B · 进程内 APScheduler （backend/app/scheduler.py）

Docker 部署无宿主 crontab，改用进程内 BackgroundScheduler，在 uvicorn 里跑同样脚本。

总开关
SECURITY_HOT_SCHEDULER_ENABLED=1 默认 OFF（docker-compose 的 web 服务已置位）
装配点
main.py:_lifespan 注入 4 个 0 参回调（避免 import 环），见 main.py:79
线程池
ThreadPool(2) · coalesce=True · max_instances=1 · misfire_grace_time=300
⚠ 禁忌
勿与 uvicorn --reload 同开——reload 监督进程可能短暂重叠，导致作业重复
job id触发默认回调 → 链式步骤
fetch_newsinterval15min_sched_fetch_news → fetch news --incremental
heavy_pipelineinterval2h_sched_heavy_pipeline → embed → cluster → classify → summarize

并发与锁模型

手动 POST /api/refresh ─┐ (token 鉴权) │ ▼ scheduler 4 个 job ──▶ _run_pipeline_steps() ──▶ 取 _refresh_lock (threading.Lock) │ │ │ 已在飞行? ─是─▶ 跳过(skip) ▼ │否 每步 subprocess.run(uv run …, timeout=3600s) │ 推进 UI stage: fetching → classifying → summarizing

单一互斥点：main.py:437 _refresh_lock + _refresh_in_flight 标志。调度作业与手动刷新共享它 → 同进程内永不重叠，crash 也在 finally 释放。

04 评审发现与建议

Warning 模式 A / B 跨进程不共享锁，同开有真重叠风险

_refresh_lock 是 进程内 threading.Lock。cron（独立进程）与进程内 scheduler（uvicorn 进程）不共享该锁。若两者被同时启用，二者的抓取/LLM 子进程会真正并发，可能引发 SQLite 写竞争与重复 LLM 花费。

建议：文档已说明"二选一"，但缺少运行时护栏。可在 scheduler 启动时检测宿主 crontab 是否含本仓库条目并告警；或用文件锁（如 flock backend/cache/.pipeline.lock）做跨进程互斥。

Warning Kafka 投毒投送（poisoning_dispatch.py）未纳入任何调度

最近提交 e877d5d feat(poisoning) 加入了 Kafka 供应链投毒情报投送，但 poisoning_dispatch.py 既不在 cron-template，也不在 in-process scheduler——目前只能手动跑。供应链投毒情报的时效性诉求高，手动驱动等于链路断点。

建议：在两种模式各加一条（如紧随 summarize 之后），保持幂等标记 poisoning_dispatched 防重发。

Info 运维脚本未调度（prune_old_articles / refresh_progress）

prune_old_articles.py（清理旧文章）与 refresh_progress.py 同样仅手动。长期运行下 news.db 会单调增长，建议为 prune 加一条每日 cron / job。

Info 墨菲首跑仅回看 4 小时

新部署且无缓存时，墨菲只回看 MURPHY_INITIAL_LOOKBACK_MINUTES=240 分钟，初始数据量很小。属设计取舍（避免大回填），但首部署预期需知晓——必要时临时调大该变量做一次性回填。

Info 解耦设计值得肯定

抓取与 LLM 富化经 SQLite WAL 完全解耦（0 import、WHERE llm_score IS NULL 拉取），抓取层 fail-soft（墨菲缺 code 即禁用而非崩溃），data.py 30s TTL 内存缓存 + 启动不预加载——这些都是稳健的工程取舍。

一句话结论

架构分层清晰、抓取/富化解耦得当。墨菲接入完整落在 抓取(fetch_data.py:476) → 归一化(data.py:473) → 服务(/api/vuln) 三层，调度上归"other"桶每 4h 刷新。调度双模式（cron / APScheduler）逻辑一致、靠单一进程内锁串行。主要待办是把 Kafka 投毒投送与 prune 纳入自动调度，并为"双模式同开"加跨进程护栏。
